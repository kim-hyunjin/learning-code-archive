출발점: 검색 공간을 줄여야 한다

큰 테이블에서 특정 행을 찾는 가장 단순한 방법은 Full Table Scan이다. 힙(heap)의 모든 페이지를 처음부터 끝까지 읽으면 언젠가는 원하는 행을 만난다. 문제는 비용이다.

행 하나가 128바이트이고 행이 10억 개, 페이지 크기가 8KB라고 하자.

Text페이지당 행 수 = 8,192 / 128 ≈ 64행
전체 페이지 수 = 1,000,000,000 / 64 ≈ 15,625,000 페이지
전체 크기      ≈ 15,625,000 × 8KB ≈ 122GB

WHERE id = 999991931 하나를 찾기 위해 최악의 경우 1,500만 번 이상의 페이지 읽기가 필요하다. 순차 읽기라 랜덤 읽기보다는 빠르지만, 초당 1GB를 읽는 스토리지에서도 2분이 넘는다. 트랜잭션 하나에 쓸 수 있는 시간이 아니다.

IDName
1John
2Ali
……
591828736Chip
……
999991931Kory

ID = 5는 첫 페이지에서 바로 찾을 수 있지만 ID = 999991931은 사실상 전부를 읽어야 한다. 그래서 필요한 것이 검색 공간(search space)을 줄여 주는 별도의 자료구조, 즉 인덱스다.

왜 이진 탐색 트리로는 안 되는가

정렬된 데이터에서의 검색이라면 이진 탐색 트리(BST)나 AVL 트리, 레드-블랙 트리를 떠올리는 게 자연스럽다. 실제로 시간 복잡도는 모두 O(log N)이다. 그런데도 디스크 기반 데이터베이스는 이들을 인덱스로 쓰지 않는다. 이유는 복잡도의 밑(base)이 다르기 때문이다.

메모리 자료구조의 비용 모델은 “비교 연산 횟수”다. 디스크 자료구조의 비용 모델은 “디스크 페이지를 몇 번 읽는가” 다. 이 둘은 자릿수가 다르다.

접근대략적인 지연 시간비율
L1 캐시 참조~1ns1
메인 메모리 참조~100ns100
NVMe SSD 랜덤 읽기~100μs100,000
HDD 랜덤 읽기 (seek 포함)~10ms10,000,000

이진 트리는 노드 하나에 키 하나만 담는다. 노드마다 자식이 둘뿐이므로 10억 개 항목에 대한 트리 높이는 log₂(10⁹) ≈ 30이다. 각 노드가 디스크의 서로 다른 위치에 흩어져 있으므로, 검색 한 번에 약 30번의 랜덤 IO가 발생한다. SSD에서도 3ms, HDD라면 300ms다.

게다가 디스크는 바이트 단위로 읽을 수 없다. 최소 단위가 페이지(Postgres 8KB, MySQL InnoDB 16KB)다. 16바이트짜리 이진 트리 노드 하나를 읽으려고 8KB를 읽어 오면 나머지 8,176바이트를 버리는 셈이다.

여기서 결론이 나온다.

디스크 자료구조는 높이를 줄이고, 한 번 읽은 페이지를 최대한 활용해야 한다. 그러려면 노드 하나에 키를 최대한 많이 담아야 한다.

이것이 B-Tree의 설계 동기다. 1 노드 = 1 디스크 페이지로 맞추고, 그 페이지 안에 수백 개의 키를 담아 자식을 수백 개로 분기시킨다. 밑이 2인 로그를 밑이 수백인 로그로 바꾸는 것이다.

Text이진 트리   : log₂(10억)   ≈ 30 레벨  → 랜덤 IO 30회
B-Tree(400) : log₄₀₀(10억) ≈ 3.5 레벨 → 랜덤 IO 4회

B-Tree의 구조

정의와 불변식

차수(order/degree)가 m인 B-Tree는 다음을 만족한다.

  • 모든 노드는 최대 m개의 자식과 최대 m-1개의 키를 가진다
  • 루트를 제외한 모든 노드는 최소 ⌈m/2⌉ - 1개의 키를 가진다 (최소 채움률 약 50%)
  • 노드 안의 키는 정렬되어 있고, 키 사이사이에 자식 포인터가 놓인다
  • 모든 리프 노드는 같은 깊이에 있다 (완전 균형)

마지막 조건이 핵심이다. B-Tree는 삽입/삭제 시 회전(rotation)이 아니라 분할(split)과 병합(merge) 으로 균형을 유지하며, 트리가 위로 자란다. 덕분에 어떤 키를 찾든 읽는 페이지 수가 트리 높이를 넘지 않는다.

여기서 두 가지를 구분해 두자.

  • “항상 높이만큼 읽는다”는 뜻은 아니다. B-Tree는 모든 노드가 value를 함께 들고 있으므로, 찾는 키가 루트나 내부 노드에 있으면 거기서 탐색이 끝난다. 아래 예시에서 2나 4를 찾는다면 루트 페이지 한 번으로 답이 나온다. 즉 트리 높이는 최악의 경우에 대한 상한이고, 실제 페이지 접근 수는 키가 어느 레벨에 있느냐에 따라 달라진다.
  • “페이지 접근”과 “물리적 디스크 IO”도 다르다. 상위 레벨 페이지는 접근 빈도가 높아 버퍼 풀에 상주하는 경우가 많고, 그때는 페이지를 읽어도 디스크까지 가지 않는다.

뒤에서 보겠지만 B+Tree는 반대로 항상 리프까지 내려간다. 운 좋은 조기 종료를 포기하는 대신 모든 조회의 비용이 같아져, 응답 시간 예측이 중요한 OLTP에서는 오히려 이쪽이 다루기 쉽다.

노드의 내용

B-Tree에서는 모든 노드(루트, 내부, 리프)의 모든 엔트리가 key와 value를 함께 가진다. 여기서 value는 보통 실제 행을 가리키는 데이터 포인터다.

  • PostgreSQL: TID(tuple id) — (페이지 번호, 페이지 내 오프셋), 6바이트
  • MySQL InnoDB: Primary Key 값
Text         [2:702 | 4:704]          ← Root Node
        /       |       \
  [1:701]   [3:703]   [5:705]     ← Leaf Nodes

5:705에서 5는 키, 705는 그 행이 저장된 위치를 가리키는 포인터다.

검색 과정

ID = 3 찾기

  1. 루트 페이지를 읽는다 (IO 1) → 2, 4 확인
  2. 2 < 3 < 4 이므로 가운데 자식으로 이동
  3. 리프 페이지를 읽는다 (IO 2) → 3:703 발견
  4. TID 703으로 힙 페이지를 읽는다 (IO 3) → 실제 행 획득

노드 안에서 키를 찾는 것은 이미 메모리에 올라온 페이지 안에서의 이진 탐색이므로 사실상 공짜다. 비용은 오직 페이지를 몇 개 읽었는가로 결정된다.

항목이 11개로 늘어난 B-Tree는 이렇게 자란다.

Text              [4:704 | 8:802]              ← Root
             /       |       \
      [2:702]    [6:800]    [10:804]       ← Internal
       /   \      /   \       /    \
 [1:701][3:703][5:705][7:801][9:803][11:805] ← Leaf

B-Tree 시각화 도구: https://www.cs.usfca.edu/~galles/visualization/BTree.html

삽입과 분할

키를 넣을 리프에 자리가 없으면 노드를 반으로 쪼개고(split), 가운데 키를 부모로 올린다. 부모도 가득 차 있으면 부모를 다시 쪼갠다. 이 연쇄가 루트까지 도달하면 루트가 분할되고 트리의 높이가 1 증가한다. B-Tree가 아래가 아니라 위로 자라는 이유이자, 모든 리프의 깊이가 항상 같은 이유다.

삭제는 반대다. 노드의 채움률이 최소치 아래로 떨어지면 형제에게서 키를 빌리거나 (borrow/redistribute) 형제와 병합(merge)한다.

fanout: 이 모든 것을 결정하는 숫자

트리의 높이는 fanout(노드 하나가 가지는 자식 수) 이 결정한다. 그리고 fanout은 페이지 크기 ÷ 엔트리 크기다. 엔트리를 작게 만들수록 트리가 낮아지고 IO가 줄어든다.

PostgreSQL의 8KB 페이지에 BIGINT 키를 인덱싱한다고 하자. 먼저 엔트리 하나의 크기를 구한다.

Text페이지에서 실제로 쓸 수 있는 공간
  8,192B - 페이지 헤더 24B - btree special area 16B ≈ 8,152B

엔트리 하나
  IndexTuple 헤더 8B + 키(BIGINT) 8B = 16B
  + 페이지 내 라인 포인터 4B
  = 20B

여기서 리프 페이지와 내부 페이지를 나눠서 계산해야 한다. PostgreSQL의 fillfactor(btree 기본값 90)는 리프 페이지의 채움률을 가리키는 설정이고, 내부(non-leaf) 페이지는 인덱스 생성 시 별도 상수인 BTREE_NONLEAF_FILLFACTOR = 70%를 목표로 채운다. 이 둘을 뭉뚱그리면 분기 수를 과대평가하게 된다.

Text리프 페이지 용량  L = 8,152 × 0.90 / 20 ≈ 367  →  약 360 엔트리
내부 노드 fanout  F = 8,152 × 0.70 / 20 ≈ 285  →  약 280 자식

이제 높이별 수용량이 나온다. 높이 h인 트리는 루트 아래로 h-1번 분기하므로 리프 페이지가 F^(h-1)개이고, 리프 하나에 L개의 엔트리가 들어가므로 총 행 수는 F^(h-1) × L이다.

트리 높이 h리프 페이지 수 F^(h-1)담을 수 있는 행 수 × L최대 페이지 접근
2280280 × 360 ≈ 10만2
3280² = 78,40078,400 × 360 ≈ 2,800만3
4280³ ≈ 2,195만2,195만 × 360 ≈ 79억4

정확한 값은 키 타입, fillfactor 설정, 중복 키 압축(PostgreSQL 13+의 deduplication), InnoDB의 16KB 페이지 등에 따라 달라지므로 자릿수 감각을 잡는 근사치로 보면 된다. 그래도 결론은 견고하다. 10억 행 테이블이라도 인덱스 높이는 4 정도이며, 상위 레벨은 버퍼 풀에 상주하므로 실제 디스크 IO는 리프 1회 + 힙 1회 수준으로 떨어진다.

fanout이 왜 중요한지는 반대로 생각하면 분명하다. 키가 UUID(16B)나 긴 문자열이면 엔트리가 커지고 fanout이 떨어지며 트리가 높아진다. 인덱스 키를 작게 유지하라는 조언은 여기서 나온다.

B-Tree의 두 가지 한계

1. 내부 노드가 value를 들고 있어 fanout을 낭비한다

B-Tree는 모든 노드에 key + value를 저장한다. 그런데 내부 노드의 value는 탐색에 전혀 쓰이지 않는다. 내부 노드가 하는 일은 “어느 자식으로 내려갈지” 결정하는 것뿐이고, 그 판단에 필요한 것은 키뿐이다. value는 순수한 공간 낭비이며, 그 공간만큼 자식 수가 줄어 트리가 높아진다.

value가 6바이트 TID라면 손해는 크지 않다. 그러나 value가 행 전체라면(클러스터드 인덱스), 내부 노드 하나에 겨우 몇 개의 키만 들어가면서 fanout이 붕괴한다.

2. 범위 쿼리가 느리다

SQLSELECT * FROM t WHERE id BETWEEN 4 AND 9;

B-Tree에서 이 쿼리를 처리하려면 중위 순회(in-order traversal) 를 해야 한다. 값이 트리 전체에 흩어져 있기 때문이다. 위 11개짜리 트리를 보자.

  • 4는 루트에 있다
  • 5는 루트의 두 번째 서브트리 → 6:800의 왼쪽 리프
  • 6은 내부 노드에 있다
  • 7은 다시 리프
  • 8은 루트에 있다
  • 9는 오른쪽 서브트리의 리프

즉 리프와 내부 노드를 오르내리며 트리를 헤집고 다녀야 하고, 접근 패턴이 랜덤이다. 읽기 순서를 미리 알 수 없으니 스토리지의 prefetch/readahead도 활용할 수 없다. 정렬된 결과가 필요한 ORDER BY, LIMIT, 페이징도 같은 문제를 겪는다.

실무 쿼리의 상당수는 점 조회(point lookup)가 아니라 범위 조회다. created_at > ?, status = ? ORDER BY id LIMIT 20, BETWEEN 같은 것들 말이다.

B+Tree: 두 문제를 한 번에 해결하다

B+Tree는 B-Tree에 두 가지 변경을 가한다.

  1. value는 리프 노드에만 저장한다. 내부 노드에는 키(정확히는 자식을 가르는 구분자, separator key)만 둔다.
  2. 리프 노드들을 링크드 리스트로 연결한다. (InnoDB와 PostgreSQL은 양방향)
Text                        [ 5 | 9 ]                        ← Root (구분자 키만)
                     /      |      \
             [ 3 ]      [ 7 ]      [ 11 ]                ← Internal (구분자 키만)
            /    \      /   \      /    \
  Leaf:  [1:701 2:702] [3:703 4:704] [5:705 6:800] ...   ← Leaf (key+value)
            ↕            ↕             ↕
         ←──────────── 양방향 링크 ────────────→

여기서 주의할 점 하나. 내부 노드의 키는 리프에 다시 등장한다. 내부 노드의 5는 데이터가 아니라 “5 미만은 왼쪽, 5 이상은 오른쪽”이라는 이정표이고, 실제 5:705는 리프에 있다. 그래서 B+Tree는 키를 약간 중복 저장하지만, 그 대가로 얻는 것이 훨씬 크다.

효과 1: fanout이 커지고 트리가 낮아진다

내부 노드에서 value가 사라지면 같은 페이지에 더 많은 구분자를 담을 수 있다. 특히 모든 데이터가 리프에만 있으므로 내부 노드 전체의 크기가 작아진다.

앞의 수치(L≈360, F≈280)로 10억 행 인덱스를 쌓아 보면 크기 차이가 분명해진다.

Text리프 페이지      1,000,000,000 / 360 ≈ 2,778,000 페이지 ≈ 21GB
그 위 레벨       2,778,000 / 280    ≈     9,921 페이지
그 위 레벨       9,921 / 280        ≈        36 페이지
루트                                =         1 페이지
────────────────────────────────────────────────────────
내부 노드 합계   ≈ 9,958 페이지 ≈ 78MB   (전체 인덱스의 약 0.4%)

이것이 결정적이다. 21GB짜리 인덱스라도 탐색에 필요한 내부 노드는 78MB뿐이라 통째로 메모리에 상주시킬 수 있다. 그러면 조회당 디스크 IO는 리프 접근 1회로 줄어든다. 내부 노드에 value를 함께 저장했다면 이 78MB가 몇 배로 불어난다.

효과 2: 범위 쿼리가 순차 접근이 된다

SQLSELECT * FROM t WHERE id BETWEEN 4 AND 9;
  1. 루트 → 내부 → 리프로 내려가 시작점 4를 한 번만 찾는다 (높이만큼의 IO)
  2. 리프의 링크를 따라 5, 6, 7, 8, 9를 옆으로 읽어 나간다
  3. 9를 넘어서면 멈춘다

핵심은 트리를 다시 탐색하지 않는다는 점이다. B-Tree라면 값 하나를 읽을 때마다 루트부터 다시 내려가야 했지만, B+Tree는 한 번 내려간 뒤로는 리프 레벨에서 옆으로만 이동한다. N개를 읽는 비용이 N × 트리 높이에서 트리 높이 + N으로 바뀐다.

잠깐, readahead가 뭔가?

readahead(선행 읽기, prefetch) 는 “지금 요청한 블록 다음 블록도 곧 필요할 것” 이라고 예측해서 요청하기 전에 미리 읽어 두는 최적화다. OS 커널, 스토리지 컨트롤러, DBMS가 각자 층위에서 수행한다.

readahead가 없다면 페이지 N개를 순서대로 읽는 과정은 이렇게 흘러간다.

Textreadahead 없음 (매번 요청 → 대기 → 처리)
  요청 P1 ─── 대기 100μs ───▶ 처리
                              요청 P2 ─── 대기 100μs ───▶ 처리
                                                          요청 P3 ─ ...
  총 시간 ≈ N × 100μs        ← 지연 시간이 N번 그대로 누적된다

readahead 있음 (순차 패턴 감지 후 미리 당겨옴)
  요청 P1 ─── 대기 100μs ───▶ 처리
       └ 커널이 P2..P16을 미리 읽어 캐시에 올려 둠
                              P2 요청 → 캐시 히트(즉시)
                              P3 요청 → 캐시 히트(즉시) ...
  총 시간 ≈ 100μs + α        ← 지연 시간이 한 번으로 압축된다

핵심은 디스크의 대역폭이 아니라 지연 시간(latency)을 숨긴다는 데 있다. SSD는 대역폭이 넉넉하지만 요청 하나하나의 왕복 지연은 여전히 존재하고, 그 지연을 N번 순서대로 기다리는 것이 순차 스캔의 진짜 비용이다. readahead는 이 왕복을 병렬화·일괄화해서, 작은 요청 여러 번을 큰 요청 몇 번으로 바꾼다.

각 층에서 실제로 동작하는 것들은 다음과 같다.

층위메커니즘
Linux 커널파일에 대한 순차 접근을 감지하면 뒤따르는 페이지를 미리 읽는다 (blockdev --setra로 조정)
PostgreSQLeffective_io_concurrency로 여러 페이지 읽기를 동시에 요청한다. OS 캐시 readahead에도 상당 부분 의존한다
MySQL InnoDB익스텐트(1MB) 안에서 순차 접근이 감지되면 다음 익스텐트를 통째로 당겨온다 (linear read-ahead, innodb_read_ahead_threshold)

그리고 여기가 요점이다. 이 모든 메커니즘은 “접근 패턴이 순차적으로 보일 때”만 발동한다. 페이지 번호가 뒤죽박죽이면 커널도 InnoDB도 다음에 무엇을 읽을지 예측할 수 없어 readahead가 꺼지고, 그러면 위의 첫 번째 그림으로 돌아간다.

그래서 링크가 보장하는 것과 보장하지 않는 것

리프 링크가 보장하는 것은 키의 논리적 순서이지, 디스크상의 물리적 인접성이 아니다. 갓 생성했거나 REINDEX / OPTIMIZE TABLE로 재구축한 인덱스는 리프가 키 순서대로 붙어 있어 위의 readahead 이점을 그대로 받는다. 그러나 랜덤 삽입과 페이지 분할이 누적되면 논리적으로 이웃한 리프가 디스크상 멀리 떨어지고(뒤의 “페이지 분할과 단편화” 참고), 그때 범위 스캔은 링크를 따라가면서도 물리적으로는 랜덤 읽기를 하게 된다.

리프 링크가 확실히 없애 주는 것은 반복적인 루트 탐색이다. 물리적 순차성은 인덱스가 정돈되어 있을 때 따라오는 보너스다.

PostgreSQL에서는 pg_stats의 correlation 값(논리적 순서와 물리적 순서의 상관 계수, 1에 가까울수록 정돈됨)으로 이 상태를 가늠할 수 있고, 플래너도 이 값을 보고 인덱스 스캔 비용을 추정한다.

ORDER BY id, LIMIT/OFFSET 페이징, MIN()/MAX(), 커서 기반 페이징이 모두 같은 이유로 빨라진다. 리프 레벨 자체가 정렬된 연결 리스트이기 때문이다.

효과 3: 리프 레벨만 훑으면 전체 스캔이 된다

인덱스만으로 답할 수 있는 쿼리(covering index / index-only scan)에서는 힙에 가지 않고 리프 체인만 순회하면 된다. COUNT(*)나 집계에도 유리하다.

용어에 대한 주의

MySQL과 PostgreSQL 문서 모두 인덱스 타입을 “B-tree” 라고 부르지만, 실제 구현은 거의 예외 없이 B+Tree 다. PostgreSQL의 nbtree는 정확히는 동시성을 위해 각 레벨에 오른쪽 형제 포인터를 둔 Lehman-Yao B-link tree 변형이다. 문서의 “B-tree”를 문자 그대로의 B-Tree로 읽지 않는 편이 좋다.

MySQL InnoDB: 클러스터드 인덱스

InnoDB의 테이블은 그 자체가 Primary Key로 정렬된 B+Tree다 (Index Organized Table). 별도의 힙이 없다.

TextPrimary Key(클러스터드) B+Tree
   Leaf = [PK | 나머지 컬럼 전부]   ← 리프가 곧 테이블 데이터

Secondary Index B+Tree
   Leaf = [인덱스 키 | PK 값]      ← 힙 포인터가 아니라 PK를 저장

bookmark lookup: 세컨더리 인덱스는 왜 두 번 탐색하는가

PostgreSQL의 세컨더리 인덱스는 리프에 TID, 즉 “힙의 몇 번 페이지, 몇 번째 슬롯” 이라는 물리적 주소를 담는다. 주소를 알고 있으니 힙 페이지 하나만 곧장 읽으면 된다.

반면 InnoDB의 세컨더리 인덱스는 리프에 PK 값을 담는다. 물리적 주소가 아니라 논리적 식별자다. 그래서 실제 행에 닿으려면 그 PK를 들고 클러스터드 인덱스를 루트부터 다시 탐색해야 한다. 이 되돌아가기를 bookmark lookup (또는 back to index / 북마크 조회)이라고 부른다.

SQL-- users(id BIGINT PK, email VARCHAR, name VARCHAR, ...)
-- INDEX idx_email (email)
SELECT name FROM users WHERE email = 'a@b.com';
Text1) 세컨더리 인덱스 idx_email 탐색            ← 높이만큼 페이지 접근 (예: 3)
     리프에서 발견: ['a@b.com' | id=1234]
     └ 여기에는 name이 없다. 있는 것은 PK뿐.

2) 클러스터드 인덱스(PK)를 id=1234로 재탐색   ← 다시 높이만큼 (예: 3)
     리프에서 발견: [1234 | email, name, ...]  ← 리프가 곧 행 전체
     └ 여기서 name을 얻는다.

합계: 트리 탐색 2회

왜 이렇게 만들었나? InnoDB의 리프는 곧 행 데이터이므로, 페이지 분할이나 행 이동이 일어나면 행의 물리적 위치가 바뀐다. 세컨더리 인덱스가 물리적 주소를 들고 있었다면 행이 움직일 때마다 모든 세컨더리 인덱스를 갱신해야 한다. PK 값은 변하지 않으므로 그럴 필요가 없다. 물리적 안정성을 얻는 대신 조회 시 한 번 더 탐색하는 것이다.

언제 두 번째 탐색이 사라지나? 필요한 컬럼이 세컨더리 인덱스 안에 전부 들어 있을 때다(covering index). 위 쿼리라면 INDEX idx_email_name (email, name)을 만들면 1단계 리프에서 name까지 얻을 수 있어 클러스터드 인덱스로 돌아갈 일이 없다. EXPLAIN의 Extra에 Using index가 찍히면 커버링이 된 것이다.

PK 크기가 모든 인덱스에 전파된다

PK 값이 모든 세컨더리 인덱스의 모든 리프 엔트리에 복제되므로, PK 타입 선택의 비용이 인덱스 개수만큼 곱해진다.

PK 타입크기세컨더리 인덱스 5개일 때 1억 행 기준 추가 비용
BIGINT8B8B × 1억 × 5 ≈ 4GB
BINARY(16) (UUID)16B16B × 1억 × 5 ≈ 8GB
CHAR(36) (UUID 문자열)36B36B × 1억 × 5 ≈ 18GB

크기가 커지면 그만큼 fanout이 떨어져 세컨더리 인덱스의 높이까지 함께 올라간다. UUID를 PK로 써야 한다면 최소한 CHAR(36)이 아니라 BINARY(16)으로 저장할 일이다.

PostgreSQL: 힙 + 세컨더리 인덱스

PostgreSQL에는 클러스터드 인덱스가 없다. 데이터는 힙에 있고, PK를 포함한 모든 인덱스가 동등하게 세컨더리 인덱스이며 리프에 TID(6B)를 저장한다.

  • PK 크기가 다른 인덱스로 전파되지 않는다. 모든 인덱스가 6바이트 TID만 저장한다
  • 대신 인덱스 조회는 항상 힙 접근이 필요하다. InnoDB의 클러스터드 인덱스처럼 “리프가 곧 데이터”인 경우가 없다
  • bookmark lookup은 없다. TID가 곧 물리적 주소이므로 힙 페이지 하나를 바로 읽는다

visibility map과 VACUUM: index-only scan의 전제 조건

PostgreSQL은 MVCC를 위해 행의 가시성 정보(어느 트랜잭션이 만들었고 지웠는지)를 힙 튜플에만 저장한다. 인덱스 엔트리에는 없다. 그래서 원칙적으로는 인덱스에서 값을 찾아도 “이 행이 지금 내 트랜잭션에 보이는 행인가” 를 확인하러 힙에 가야 한다. 인덱스 안에 필요한 컬럼이 다 있어도 마찬가지다.

이 확인을 건너뛰게 해 주는 것이 visibility map(VM) 이다. 힙 페이지당 2비트짜리 아주 작은 비트맵으로, 그중 all-visible 비트는 “이 페이지의 모든 튜플은 현재 모든 트랜잭션에게 보인다” 를 뜻한다.

Textindex-only scan의 판단 흐름

인덱스 리프에서 (키, TID) 획득
        │
        ├─ VM에서 TID의 힙 페이지가 all-visible?
        │        │
        │        ├─ YES → 힙 접근 생략. 인덱스 값만으로 결과 반환  ✅
        │        └─ NO  → 힙 페이지를 읽어 가시성 확인 (heap fetch) ❌

그런데 이 all-visible 비트를 세워 주는 것이 VACUUM이다. 따라서:

  • INSERT/UPDATE가 들어온 직후의 페이지는 all-visible이 아니다. 방금 대량 적재한 테이블은 인덱스가 완벽해도 index-only scan이 힙을 읽는다
  • autovacuum이 뒤처지면(대량 갱신, 긴 트랜잭션이 오래 열려 있어 정리가 밀리는 경우) index-only scan을 노린 설계가 조용히 무력화된다
  • EXPLAIN (ANALYZE, BUFFERS)의 Heap Fetches: 값이 이 상태를 그대로 보여 준다. Heap Fetches: 0이면 의도대로 동작한 것이고, 숫자가 크면 이름만 index-only scan이다
SQLEXPLAIN (ANALYZE, BUFFERS) SELECT id FROM t WHERE id BETWEEN 100 AND 200;
--  Index Only Scan using t_pkey on t  (actual rows=101 ...)
--    Heap Fetches: 101      ← VM이 안 서 있다. VACUUM 후 0이 된다
VACUUM (ANALYZE) t;

정리하면, PostgreSQL의 index-only scan은 인덱스 설계만으로 얻어지지 않고 VACUUM 상태에 의존한다. InnoDB의 covering index가 구조만으로 성립하는 것과 대조되는 지점이다.

HOT update: 인덱스 갱신을 피하는 장치

PostgreSQL의 UPDATE는 제자리 수정이 아니라 새 튜플을 쓰고 옛 튜플을 죽은 것으로 표시하는 방식이다. 새 튜플은 위치가 다르므로 TID가 바뀌고, 원칙대로라면 그 테이블의 모든 인덱스가 새 TID를 가리키도록 갱신되어야 한다. 인덱스가 5개면 UPDATE 한 번에 B+Tree 6개를 건드리는 셈이다.

HOT(Heap-Only Tuple) update는 두 조건이 맞을 때 이 비용을 없앤다.

  1. 갱신된 컬럼 중 인덱싱된 것이 하나도 없다 — 인덱스의 키 값이 안 변했다는 뜻
  2. 새 버전을 같은 힙 페이지 안에 넣을 자리가 있다

이때는 인덱스를 전혀 건드리지 않고, 옛 튜플에서 새 튜플로 이어지는 페이지 내부 포인터 체인만 만든다. 인덱스는 계속 옛 TID를 가리키고, 조회 시 그 페이지에서 체인을 따라가 최신 버전을 찾는다.

Text[힙 페이지 7]
  슬롯 2: (구버전) ──HOT chain──▶ 슬롯 9: (신버전)
     ▲
     └── 인덱스는 여전히 (7,2)를 가리킨다. 인덱스 갱신 0회.

실무에서 끌어낼 수 있는 것은 두 가지다.

  • 자주 갱신되는 컬럼에는 인덱스를 만들지 않는다. 인덱스 하나 때문에 HOT이 깨지면 그 테이블의 모든 UPDATE가 전체 인덱스 갱신으로 바뀐다
  • fillfactor를 낮춰 페이지에 여유 공간을 둔다. 갱신이 잦은 테이블에 ALTER TABLE t SET (fillfactor = 80)처럼 설정하면 같은 페이지에 새 버전이 들어갈 자리가 남아 HOT 성공률이 올라간다 (기본값은 힙 100, btree 90)

B+Tree의 대가

B+Tree는 만능이 아니다. 읽기에 최적화된 구조인 만큼 쓰기에서 값을 치른다.

페이지 분할(page split)과 단편화. 삽입 위치가 랜덤하면 가득 찬 리프가 계속 쪼개진다. 분할된 페이지는 각각 절반만 차서 인덱스 크기가 부풀고(bloat), 논리적 순서와 물리적 순서가 어긋나 범위 스캔의 순차성이 무너진다.

쓰기 증폭(write amplification). 8바이트 키 하나를 추가해도 8KB 페이지 전체가 더티가 되어 다시 쓰인다. 여기에 WAL 기록까지 더해진다.

인덱스 개수만큼 곱해지는 쓰기 비용. INSERT 한 번은 테이블 쓰기 한 번이 아니라 1 + 인덱스 개수만큼의 B+Tree 갱신이다. 쓰지 않는 인덱스는 순수한 손해다.

이 때문에 쓰기가 압도적으로 많은 워크로드에서는 LSM Tree(RocksDB, Cassandra, ScyllaDB 등)를 쓴다. LSM은 쓰기를 메모리에 모아 순차적으로 flush해 랜덤 쓰기를 없애는 대신, 읽기 시 여러 SSTable을 확인해야 하고 컴팩션 비용을 부담한다. B+Tree는 읽기 최적화, LSM Tree는 쓰기 최적화라는 트레이드오프다.

실무로 옮기면

지금까지 본 구조에서 인덱스 설계 원칙이 거의 기계적으로 따라 나온다.

  • 랜덤 PK를 피하라. 삽입 위치는 키 값이 결정한다. UUIDv4처럼 무작위인 키는 트리 전역에 페이지 분할을 일으키고 작업 집합을 인덱스 전체로 넓힌다
  • 인덱스 키를 작게 유지하라. 키 크기가 fanout을 정하고, fanout이 트리 높이를 정한다. 긴 문자열에는 접두사 인덱스나 해시 컬럼을 쓴다
  • 복합 인덱스의 컬럼 순서가 곧 정렬 순서다. (a, b) 리프는 a로 먼저 정렬되고 a가 같은 것끼리 b로 정렬된다. 그래서 b 단독 조건은 연속 구간이 아니다
  • 범위 조건 컬럼은 뒤로 보내라. 범위 조건이 걸린 순간부터 뒤쪽 컬럼의 정렬이 깨져, 구간을 좁히지 못하고 읽은 뒤 버리는 필터가 된다
  • 커버링 인덱스를 활용하라. 리프에 필요한 값이 다 있으면 InnoDB의 bookmark lookup이나 PostgreSQL의 힙 접근이 통째로 사라진다

각 원칙의 근거와 예외, 그리고 접두사 인덱스의 N을 정하는 법이나 PostgreSQL INCLUDE 절의 쓰임 같은 구체적인 적용 방법은 별도 글로 정리했다.

핵심을 한 줄로 줄이면 이렇다.

B+Tree는 “탐색에 필요한 것(키)“과 “결과에 필요한 것(값)“을 분리해서, 상위 레벨은 메모리에 올리고 리프 레벨은 정렬된 연결 리스트로 만든 구조다.
