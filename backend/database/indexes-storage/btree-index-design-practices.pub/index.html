B+Tree 구조에서 끌어내는 인덱스 설계 원칙 5가지

PK 선택, 키 크기, 복합 인덱스 순서, 범위 조건 배치, 커버링 인덱스. 흔히 통용되는 인덱스 설계 규칙들이 B+Tree의 어떤 구조적 성질에서 나오는지 따라가며 정리한다.

인덱스 설계 규칙은 대개 결론만 외워서 쓰게 된다. “UUID를 PK로 쓰지 마라”, “복합 인덱스는 순서가 중요하다” 같은 것들이다. 그런데 이 규칙들은 전부 B+Tree라는 자료구조의 성질에서 기계적으로 따라 나오는 것이라, 구조를 알고 보면 외울 것이 거의 없다. 예외가 언제 성립하는지도 그때 보인다.

이 글은 B-Tree와 B+Tree, 그리고 DB 인덱스가 B+Tree를 선택한 이유에서 다룬 구조를 전제로, 거기서 따라 나오는 실무 원칙 다섯 가지를 정리한다. fanout, 페이지 분할, 리프 링크, 클러스터드 인덱스 같은 용어는 그 글의 설명을 그대로 쓴다.

1. 랜덤 PK를 피하라

왜

B+Tree는 키 순서대로 정렬된 구조다. 그러므로 삽입 위치는 키 값이 결정한다.

AUTO_INCREMENT/BIGSERIAL처럼 단조 증가하는 키는 새 값이 항상 기존 최대값보다 크므로 트리의 가장 오른쪽 리프에만 삽입된다. 페이지가 가득 차면 그 페이지만 분할되고, 방금 만든 새 페이지가 다음 삽입을 계속 받는다. 작업 집합이 리프 몇 개로 좁혀지므로 버퍼 풀에 늘 올라와 있다.

UUIDv4는 정반대다. 값이 균등하게 무작위이므로 삽입 위치가 트리 전역에 흩어진다.

Text단조 증가 키                          UUIDv4
[..][..][..][..][가득 참]            [..][가득 참][..][가득 참][..]
                    ▲                     ▲            ▲
              여기서만 분할          매번 다른 곳에서 분할
              버퍼 풀 적중 ↑         인덱스 전체가 작업 집합 → 적중 ↓

InnoDB에서는 손해가 두 배가 된다. 테이블 자체가 PK로 정렬된 클러스터드 인덱스이므로 분할되는 페이지가 곧 행 데이터 페이지이고, 게다가 PK 값이 모든 세컨더리 인덱스의 리프에 복제되므로 크기 낭비도 인덱스 개수만큼 곱해진다.

UUIDv7 / ULID는 어디까지 해결하는가

UUIDv7과 ULID는 상위 비트에 타임스탬프를 두어 “대체로 시간 순으로 증가하는” 식별자다. 다만 정렬이 보장되는 것은 그 타임스탬프 부분까지다. 같은 밀리초 안에서 생성된 값들은 하위 랜덤 비트로 순서가 갈리므로, 초당 수천 건이 들어오거나 여러 노드에서 동시에 생성하는 상황에서는 나중에 만든 값이 직전 값보다 작을 수 있다. 그러면 오른쪽 끝 삽입이 깨진다.

오른쪽 끝 삽입을 보장하려면 같은 타임스탬프 안에서 카운터를 증가시키는 단조 증가(monotonic) 생성기를 써야 한다. ULID 명세의 monotonic factory, UUIDv7의 counter 방식이 그것이다.

그런 생성기를 쓰지 않더라도 UUIDv4에 비하면 삽입 지점이 최근 시간대의 좁은 구간으로 모이므로 분할과 버퍼 풀 낭비가 크게 줄어든다. “완전한 append-only는 아니지만 국소적” 정도로 이해하면 된다.

정리

키삽입 위치분할버퍼 풀
AUTO_INCREMENT / BIGSERIAL항상 오른쪽 끝한 지점에 국한매우 유리
UUIDv7 / ULID (monotonic 생성기)오른쪽 끝한 지점에 국한유리
UUIDv7 / ULID (기본)최근 시간대의 좁은 구간국소적대체로 유리
UUIDv4트리 전역에 무작위전역 발생불리

분산 환경 등의 이유로 UUID를 써야 한다면, 정렬 가능한 버전을 고르는 것과 별개로 저장 타입도 챙겨야 한다. CHAR(36) 문자열이 아니라 BINARY(16)으로 저장하면 크기가 절반 이하로 줄고, 그만큼 fanout이 유지된다.

단조 증가 키에도 대가는 있다. 삽입이 한 페이지에 집중되므로 쓰기가 매우 많은 환경에서는 그 페이지가 경합 지점(hot spot)이 된다. 대부분의 서비스에서는 랜덤 PK의 분할 비용이 훨씬 크지만, 극단적인 쓰기 부하라면 저울질할 문제다.

2. 인덱스 키를 작게 유지하라

왜

fanout은 페이지에서 쓸 수 있는 공간 ÷ 엔트리 크기이고, 트리 높이는 fanout의 로그로 결정된다. 키가 커지면 fanout이 떨어지고, 트리가 높아지고, 조회당 페이지 접근이 늘어난다. 인덱스 파일 크기도 함께 커져 버퍼 풀에 덜 올라간다.

그런데 VARCHAR(255) URL이나 긴 경로 문자열처럼 키가 클 수밖에 없는 경우가 있다. 이때 쓰는 우회법이 접두사 인덱스와 해시 컬럼이다.

접두사 인덱스 (prefix index)

컬럼 값 전체가 아니라 앞의 N글자만 인덱싱한다. MySQL은 문법으로 지원한다.

SQL-- url 컬럼의 앞 30바이트만 인덱싱한다
CREATE INDEX idx_url ON pages (url(30));

키가 255B에서 30B로 줄면 fanout이 몇 배로 늘고 인덱스 크기도 그만큼 작아진다. 대신 잃는 것이 있다.

  • 커버링이 안 된다. 인덱스에 값의 일부만 있으므로 원본 값이 필요하면 반드시 테이블로 돌아가야 한다
  • 정렬에 못 쓴다. ORDER BY url을 인덱스 순서로 해결할 수 없다
  • N을 잘못 잡으면 무의미하다. 앞부분이 같은 값이 많으면 (https://example.com/...처럼 공통 접두사가 긴 경우) 카디널리티가 무너져 필터링이 안 된다

그래서 N은 감이 아니라 선택도를 재서 정한다. 원본의 카디널리티 비율에 충분히 근접하는 가장 짧은 N을 고르면 된다.

SQLSELECT COUNT(DISTINCT url)            / COUNT(*) AS full,
       COUNT(DISTINCT LEFT(url, 20))  / COUNT(*) AS p20,
       COUNT(DISTINCT LEFT(url, 30))  / COUNT(*) AS p30,
       COUNT(DISTINCT LEFT(url, 50))  / COUNT(*) AS p50
FROM pages;

PostgreSQL에는 접두사 인덱스 문법이 없지만 표현식 인덱스로 같은 일을 한다. 단, 쿼리도 같은 표현식을 써야 인덱스가 쓰인다.

SQLCREATE INDEX idx_url_prefix ON pages ((left(url, 30)));
SELECT * FROM pages WHERE left(url, 30) = left($1, 30) AND url = $1;

해시 컬럼

긴 값의 해시를 별도 컬럼에 저장하고 그 컬럼을 인덱싱한다. 255B 문자열 대신 8B 정수를 인덱싱하게 되므로 크기 절감 폭이 훨씬 크다.

SQLALTER TABLE pages ADD COLUMN url_hash BIGINT;   -- 예: CRC32/xxHash 결과
CREATE INDEX idx_url_hash ON pages (url_hash);

-- 조회 시에는 해시와 원본을 함께 건다
SELECT * FROM pages WHERE url_hash = CRC32($1) AND url = $1;

url 조건을 함께 거는 것이 중요하다. 해시는 충돌할 수 있어서, 해시만으로 필터링하면 다른 URL이 섞여 들어온다. 해시로 후보를 좁히고 원본 비교로 확정하는 구조다. 제약은 분명하다.

  • 등치 비교 전용이다. 해시는 순서를 보존하지 않으므로 범위 조회, LIKE 'prefix%', ORDER BY에 전혀 쓸 수 없다
  • 컬럼과 인덱스를 추가로 유지해야 한다. 애플리케이션에서 채우기보다 생성 컬럼 (MySQL의 GENERATED, PostgreSQL의 GENERATED ALWAYS AS ... STORED)이나 트리거로 자동 갱신하는 편이 안전하다

PostgreSQL이라면 별도 컬럼 없이 해시 인덱스(USING hash)나 md5(url) 표현식 인덱스로 대신할 수도 있다. 해시 인덱스 역시 =만 지원하고 정렬·유니크 제약에는 쓸 수 없다는 점은 같다.

정리

접두사 인덱스해시 컬럼
크기 절감중간 (N바이트)큼 (8~16B 고정)
등치 조회가능 (후보 좁히기)가능 (후보 좁히기)
범위 / LIKE 'x%'가능불가
ORDER BY불가불가
추가 유지 대상없음컬럼 + 인덱스

접두사 인덱스는 범위·정렬을 일부 살리면서 크기를 줄이는 쪽, 해시 컬럼은 정확한 등치 조회에 몰아주고 크기를 극단적으로 줄이는 쪽이다.

3. 복합 인덱스의 컬럼 순서가 곧 정렬 순서다

왜

(a, b) 인덱스의 리프는 a로 먼저 정렬하고, a가 같은 것끼리 b로 정렬되어 있다. 전화번호부가 성으로 먼저 정렬되고 같은 성 안에서 이름으로 정렬되는 것과 같다.

Text(a, b) 인덱스 리프의 정렬 상태

(1, 10) (1, 20) (1, 30) (2, 10) (2, 20) (3, 10) (3, 20) (3, 30)
 └──────  a=1  ──────┘  └─  a=2  ─┘  └──────  a=3  ──────┘
            b 정렬됨         b 정렬됨          b 정렬됨

a 조건이 주어지면 그 구간이 연속된 한 덩어리이므로 시작점을 찾아 훑으면 된다. a와 b가 모두 주어지면 구간이 더 좁아진다. 그러나 b 단독 조건은 다르다. b = 10인 항목은 리프 전체에 흩어져 있어(위 예에서 1번, 4번, 6번 위치) 연속 구간이 아니다. 시작점을 특정할 수 없으니 정렬 순서를 활용할 수가 없다.

성을 모른 채 이름만으로 전화번호부에서 사람을 찾는 상황과 같다. 결국 처음부터 끝까지 넘겨 봐야 한다.

예외: skip scan

절대적인 규칙은 아니다. 선행 컬럼의 고유값이 아주 적을 때는 옵티마이저가 선행 컬럼 값 하나하나에 대해 b 구간을 반복 탐색하는 skip scan을 고를 수 있다. 위 예라면 a ∈ {1, 2, 3}이므로 (1, 10), (2, 10), (3, 10) 세 구간을 각각 찾는 식이다.

  • MySQL 8.0.13+: index skip scan
  • PostgreSQL 18+: B-tree skip scan

어디까지나 비용 기반 선택이고, 선행 컬럼의 카디널리티가 조금만 높아져도(값이 수천 개면 수천 번의 탐색이 된다) 옵티마이저가 포기한다. 설계는 여전히 선행 컬럼 기준으로 하고, skip scan은 미처 못 만든 인덱스에 대한 안전망 정도로 보는 것이 맞다.

실무 규칙

  • 여러 쿼리가 공유하는 컬럼을 앞에 둔다. (a, b) 하나로 a 조건과 a, b 조건을 모두 커버할 수 있으므로, 인덱스 개수를 줄일 수 있다
  • 선택도가 높은(= 고유값이 많은) 컬럼을 앞에 두면 구간이 빨리 좁아진다. 단, 다음 원칙과 충돌하면 다음 원칙이 우선한다

4. 범위 조건 컬럼은 뒤로 보내라

왜

리프는 선행 컬럼이 같은 구간 안에서만 후행 컬럼으로 정렬되어 있다. 그러므로 선행 컬럼에 범위 조건이 걸리면 그 시점부터 후행 컬럼의 정렬은 깨진다.

SQL-- INDEX (created_at, status) 인 경우
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND status = 'PAID';
Text(created_at, status) 리프

(01-01, CANCELED) (01-01, PAID) (01-02, NEW) (01-02, PAID) (01-03, NEW) ...
└────────────── created_at >= 01-01 인 구간 전체를 스캔 ──────────────┘
                        그 안에서 status = 'PAID'를 하나씩 걸러낸다

created_at 구간은 인덱스로 좁혔지만, status는 그 구간을 더 좁히지 못하고 읽은 뒤 버리는 필터로만 쓰인다. 1월 이후 주문이 100만 건이면 100만 개의 인덱스 엔트리를 읽는다.

순서를 뒤집으면 달라진다.

SQL-- INDEX (status, created_at)
Text(status, created_at) 리프

(CANCELED, ...) ... (NEW, ...) ... (PAID, 01-01) (PAID, 01-02) (PAID, 01-03) ...
                                   └── 여기부터 연속된 한 구간만 읽는다 ──┘

status = 'PAID'로 구간을 먼저 확정하고, 그 안에서 created_at >= '2026-01-01'의 시작점을 찾아 끝까지 읽으면 된다. 읽는 엔트리 수가 결과 행 수에 가까워진다.

규칙

등치(=, IN) 조건 컬럼을 앞에, 범위(>, <, BETWEEN, LIKE 'x%') 조건 컬럼을 뒤에 둔다. 범위 조건 컬럼 뒤에 오는 컬럼은 구간을 좁히지 못한다.

ORDER BY가 함께 있다면 한 가지 더 있다. 범위 조건 컬럼과 정렬 컬럼이 같으면 정렬까지 인덱스로 해결되지만, 다르면 별도 정렬(Using filesort / Sort 노드)이 발생한다. (status, created_at) 인덱스는 WHERE status = 'PAID' ORDER BY created_at LIMIT 20을 정렬 없이 처리한다.

EXPLAIN으로 확인할 때 MySQL의 key_len은 실제로 구간을 좁히는 데 쓰인 컬럼까지의 길이를 보여 준다. 복합 인덱스를 걸었는데 key_len이 첫 컬럼 크기에 머물러 있다면 뒤쪽 컬럼이 필터로만 쓰이고 있다는 뜻이다.

5. 커버링 인덱스를 활용하라

왜

인덱스에서 값을 찾은 뒤 실제 행을 가져오는 단계가 조회 비용의 절반 이상을 차지할 때가 많다. InnoDB에서는 bookmark lookup(세컨더리 인덱스에서 얻은 PK로 클러스터드 인덱스를 재탐색), PostgreSQL에서는 힙 접근이다.

쿼리가 필요로 하는 컬럼이 인덱스 안에 모두 들어 있으면 이 단계가 통째로 사라진다. 이것이 커버링 인덱스다.

SQLSELECT name FROM users WHERE email = ?;

CREATE INDEX idx_email_name ON users (email, name);   -- 커버링

MySQL은 EXPLAIN의 Extra에 Using index가 찍히면 커버링이 된 것이다.

PostgreSQL의 INCLUDE 절

PostgreSQL에는 이를 위한 전용 문법이 있다. INCLUDE로 지정한 컬럼은 리프 페이지에만 payload로 얹히고, 내부 노드의 구분자 키에는 들어가지 않는다.

SQL-- 두 방식 모두 위 쿼리를 커버한다
CREATE INDEX ON users (email, name);            -- name도 키의 일부
CREATE INDEX ON users (email) INCLUDE (name);   -- name은 리프에만

차이는 세 가지다.

  • fanout이 유지된다. name이 내부 노드에 들어가지 않으므로 구분자 키가 작게 유지되고, 트리 높이가 올라가지 않는다. 원칙 2와 충돌하지 않는다는 뜻이다
  • 정렬·탐색에는 쓰이지 않는다. ORDER BY email, name이나 name 조건 탐색에는 도움이 되지 않는다. 오직 행 접근을 줄이는 용도다
  • UNIQUE 제약과 함께 쓸 수 있다. UNIQUE (email) INCLUDE (name)은 email에만 유일성을 걸면서 name을 함께 담는다. (email, name) 복합 인덱스로는 불가능하다

즉 정렬이나 조건 탐색에 필요한 컬럼은 키로, 결과를 만들기 위해서만 필요한 컬럼은 INCLUDE로 두는 것이 원칙이다. InnoDB에는 INCLUDE가 없으므로 복합 인덱스의 뒤쪽 컬럼으로 같은 효과를 내되, 그만큼 키가 커진다는 점을 감수해야 한다.

PostgreSQL의 함정: VACUUM

PostgreSQL에서는 커버링 인덱스를 만들어도 그것만으로 힙 접근이 사라지지 않는다. 행의 가시성 정보가 힙에만 있어서, visibility map에 해당 페이지가 all-visible로 표시되어 있어야 힙 접근을 생략할 수 있다. 그리고 그 비트를 세워 주는 것은 VACUUM이다.

SQLEXPLAIN (ANALYZE, BUFFERS) SELECT name FROM users WHERE email = $1;
--  Index Only Scan using idx_email_name on users
--    Heap Fetches: 1        ← 0이 아니면 이름만 index-only scan이다

대량 적재 직후이거나 autovacuum이 뒤처진 상태에서는 인덱스 설계가 완벽해도 Heap Fetches가 올라간다. 자세한 내용은 원문 글의 visibility map 절을 참고.

대가

커버링 인덱스는 공짜가 아니다. 컬럼을 더 넣는 만큼 인덱스가 커지고, 쓰기 비용이 늘어난다. INSERT 한 번은 1 + 인덱스 개수만큼의 B+Tree 갱신이고, 인덱스가 커지면 버퍼 풀에서 다른 데이터를 밀어낸다. 자주 실행되는 핵심 쿼리 몇 개에만 적용하는 것이 맞다.
