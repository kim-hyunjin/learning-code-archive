이 시리즈의 마지막 글입니다. 01장에서 언급한 "전처리 → 컴파일 → 링크" 중 첫 단계인 전처리기가 실제로 무엇을 하는지, 그리고 매크로가 순수한 텍스트 치환이기 때문에 왜 위험할 수 있는지, 나아가 09~16장에서 다룬 `const`, `constexpr`, 템플릿이 오늘날 매크로의 역할 대부분을 더 안전하게 대체하는 이유를 정리합니다.

## 전처리기란

01장에서 언급했듯, 컴파일에 앞서 `#`으로 시작하는 지시문을 처리하는 단계가 전처리입니다. 이 단계는 C++ 문법을 전혀 모른 채 순수하게 **텍스트 치환**만 수행합니다.

## #define으로 상수 매크로 만들기

```cpp
#define MAX_USERS 100

int users[MAX_USERS]; // 컴파일 전에 "int users[100];"으로 그대로 치환됨
```

02장에서 `const int MAX_USERS = 100;`을 다뤘는데, 오늘날에는 매크로 상수보다 `const`(또는 `constexpr`)가 더 권장됩니다. 매크로는 타입이 없고 스코프도 없어서(전역으로 텍스트 치환), 디버거에서 이름이 보이지 않고 이름 충돌 위험도 있기 때문입니다.

## 함수처럼 쓰는 매크로

```cpp
#define SQUARE(x) ((x) * (x))

int result = SQUARE(5); // ((5) * (5)) 로 치환 → 25
```

매크로는 함수가 아니라 단순 텍스트 치환이기 때문에, 괄호를 꼼꼼히 두르지 않으면 예상치 못한 결과가 나옵니다.

```cpp
#define SQUARE_BAD(x) x * x

int result = SQUARE_BAD(2 + 3); // 2 + 3 * 2 + 3 으로 치환됨 (연산자 우선순위 때문에 11이 나옴, 25가 아님)
int resultGood = SQUARE(2 + 3);  // ((2 + 3) * (2 + 3)) → 25
```

매크로 인자에 부수 효과(증감 연산 등)가 있는 값을 넘기면 더 위험합니다.

```cpp
int i = 5;
int result = SQUARE(i++); // ((i++) * (i++)) 로 치환 → i가 두 번 증가하며 정의되지 않은 동작
```

## 조건부 컴파일

플랫폼이나 빌드 모드에 따라 다른 코드를 포함시킬 때 사용합니다.

```cpp
#define DEBUG_MODE

#ifdef DEBUG_MODE
    std::cout << "디버그 로그: 값 = " << x << "\n";
#endif

#if defined(_WIN32)
    // 윈도우 전용 코드
#elif defined(__APPLE__)
    // macOS 전용 코드
#else
    // 그 외
#endif
```

## 헤더 가드

헤더 파일이 같은 번역 단위에서 두 번 이상 포함되는 것을 막는 전통적인 방법입니다.

```cpp
// MyHeader.h
#ifndef MY_HEADER_H  // 아직 정의되지 않았다면
#define MY_HEADER_H   // 정의하고 아래 내용을 포함

class MyClass {
    // ...
};

#endif // MY_HEADER_H
```

같은 헤더가 두 번 `#include`되면, 첫 번째에서 `MY_HEADER_H`가 정의되므로 두 번째부터는 `#ifndef`가 거짓이 되어 내용이 중복 포함되지 않습니다. 대부분의 최신 컴파일러는 같은 목적의 `#pragma once`도 지원합니다.

```cpp
#pragma once // 컴파일러가 알아서 중복 포함을 막아줌, 헤더 가드보다 간결

class MyClass {
    // ...
};
```

## 매크로의 대안

현대 C++에서는 매크로가 할 수 있던 많은 일들을 더 안전한 문법으로 대체할 수 있습니다.

```cpp
// 매크로 상수 대신
const double PI = 3.14159;
constexpr int MAX_USERS = 100; // 컴파일 타임 상수임을 명시

// 매크로 함수 대신 inline 함수나 템플릿
inline int square(int x) {
    return x * x; // 함수이므로 타입 검사가 되고, 인자를 두 번 평가하는 부수효과 문제가 없음
}

template <typename T>
T maxValue(T a, T b) { // 16장에서 다룬 함수 템플릿, 여러 타입에 안전하게 대응
    return (a > b) ? a : b;
}
```

`inline`/`constexpr`/템플릿으로 작성한 코드는 컴파일러가 타입을 검사해주고, 디버거에서도 이름이 그대로 보이며, 스코프 규칙을 따르기 때문에 대부분의 상황에서 매크로보다 안전합니다.

## 매크로가 여전히 쓰이는 곳

조건부 컴파일(`#ifdef`), 헤더 가드처럼 "코드 자체를 포함할지 말지 결정"하는 용도는 언어 문법만으로는 대체할 수 없어 여전히 매크로(정확히는 전처리기 지시문)를 씁니다. 반면 "값 하나를 계산하는" 용도라면 대부분 `const`/`constexpr`/`inline`/템플릿으로 대체하는 것이 더 안전합니다.

## 흔한 실수

- 함수처럼 쓰는 매크로에서 매개변수와 전체 식을 괄호로 감싸지 않으면, 매크로가 다른 연산자와 섞이는 문맥에서 의도와 다르게 계산됩니다. 위 `SQUARE_BAD` 예시가 대표적입니다.
- 매크로는 전처리 단계에서 이름만 보고 무조건 치환되므로, 클래스 멤버나 지역 변수와 이름이 겹치면 예상치 못한 곳까지 치환되어 버립니다. 매크로 이름은 관례적으로 `ALL_CAPS`로 써서 일반 변수와 구분합니다.
