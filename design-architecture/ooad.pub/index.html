좋은 객체지향 소프트웨어는 고객이 원하는 일을 수행할 뿐 아니라, 요구사항이 바뀌어도 쉽게 확장하고 수정할 수 있어야 한다. 객체지향 분석·설계(Object-Oriented Analysis & Design, OOA&D)는 현실의 문제를 객체와 관계로 해석하고, 변화에 견디는 구조로 옮기는 과정이다.

좋은 설계가 갖춰야 할 조건

구현보다 인터페이스에 의존한다

구체적인 구현 대신 인터페이스에 맞춰 코딩하면 현재 존재하는 구현뿐 아니라 앞으로 추가할 구현도 같은 방식으로 사용할 수 있다. 호출하는 쪽과 구현체 사이의 결합이 줄어들기 때문에 기능을 교체하거나 확장하기도 쉬워진다.

변하는 부분을 캡슐화한다

캡슐화는 단순히 중복 코드를 없애는 기법이 아니다. 자주 변하는 기능을 안정적인 부분과 분리하여, 변경의 영향이 애플리케이션 전체로 퍼지지 않게 한다.

  • 데이터와 행동의 접근 범위를 제어한다.
  • 변경 가능성이 높은 기능을 별도의 객체나 모듈로 분리한다.
  • 클래스가 불필요한 변경에 노출되지 않도록 보호한다.

클래스마다 변경 이유를 하나만 둔다

소프트웨어는 계속 변한다. 변화에 잘 견디게 만드는 가장 직접적인 방법은 각 클래스가 하나의 책임에 집중하도록 하는 것이다. 클래스가 여러 역할을 맡으면 역할마다 서로 다른 변경 이유가 생기고, 작은 수정도 넓은 범위에 영향을 줄 수 있다.

높은 응집도와 느슨한 결합을 지향한다

응집도(cohesion)는 클래스, 객체, 패키지에 서로 밀접하게 관련된 책임이 모여 있는 정도다. 하나의 클래스가 몇 가지 관련된 일에 집중하면 응집도가 높고, 관련 없는 여러 일을 함께 처리하면 응집도가 낮다.

결합도(coupling)는 구성 요소가 서로 의존하는 정도다. 일반적으로 응집도가 높을수록 객체의 책임이 분명해지고 다른 객체와의 결합은 느슨해진다.

높은 응집도가 언제나 변경 용이성을 보장하는 것은 아니다. 시스템의 동작 자체를 크게 바꾸면 잘 분리된 설계도 수정해야 한다. 다만 책임이 분명한 객체는 변경 범위를 좁히고, 재사용과 확장을 쉽게 만든다.

핵심 설계 원칙

원칙핵심 내용설계에 적용하는 방법
OCP(Open–Closed Principle)확장에는 열려 있고 수정에는 닫혀 있어야 한다.기존 코드를 바꾸기보다 새로운 구현을 추가해 행동을 확장한다.
DRY(Don’t Repeat Yourself)하나의 지식이나 요구사항은 한 곳에서 표현해야 한다.공통 부분을 추출하고 적절한 추상화로 중복을 제거한다.
SRP(Single Responsibility Principle)객체는 하나의 책임과 하나의 변경 이유를 가져야 한다.서로 다른 역할을 별도의 클래스나 모듈로 나눈다.
LSP(Liskov Substitution Principle)하위 타입은 상위 타입을 사용하는 자리에 대체될 수 있어야 한다.상속 계약을 지킬 수 없다면 위임이나 구성을 검토한다.

상속 대신 행동을 재사용하는 방법

LSP를 위반하거나 상속 관계가 자연스럽지 않다면 다음 관계를 고려할 수 있다.

  • 위임(Delegation): 필요한 행동을 다른 객체에 요청한다. 해당 행동을 직접 바꿀 필요가 없을 때 유용하다.
  • 구성(Composition): 객체가 자신의 일부로 다른 객체를 소유하고 그 행동을 사용한다. 일반적으로 전체 객체가 사라지면 구성 요소도 함께 생명주기를 마친다.
  • 집합(Aggregation): 독립적으로 존재할 수 있는 객체를 참조해 행동을 사용한다. 전체 객체가 사라져도 구성원이 계속 존재할 수 있다.

분석에서 구현까지

OOA&D는 분석과 설계를 한 번에 끝내는 선형 절차가 아니다. 새로운 기능이나 유스케이스를 구현할 때마다 큰 그림과 작은 기능을 오가며 반복한다.

Text특징 목록
  → 유스케이스 다이어그램
  → 문제 분해
  → 요구사항 분석
  → 도메인 분석
  → 사전 설계
  → 구현과 테스트
  → 출시
  1. 특징 목록: 애플리케이션이 무엇을 해야 하는지 상위 수준에서 파악한다.
  2. 유스케이스 다이어그램: 시스템의 주요 프로세스와 외부 행위자의 관계를 찾는다.
  3. 문제 분해: 기능 단위로 모듈을 나누고 우선순위를 정한다.
  4. 요구사항 분석: 각 모듈의 요구사항을 구체화하고 전체 목표와 일치하는지 확인한다.
  5. 도메인 분석: 유스케이스를 도메인 객체에 연결하고 고객과 공통의 용어를 만든다.
  6. 사전 설계: 객체의 세부 책임과 관계를 정의하고 적절한 원칙과 패턴을 적용한다.
  7. 구현과 테스트: 코드를 작성하고 동작을 검증한다. 기능과 유스케이스가 완성될 때까지 이 과정을 반복한다.
  8. 출시: 완성된 결과를 사용자에게 전달한다.

특징과 유스케이스의 차이

  • 특징(feature)은 시스템이 제공해야 하는 기능이다.
  • 유스케이스(use case)는 사용자가 목표를 달성하기 위해 시스템과 상호작용하는 과정을 보여 준다.

둘은 함께 요구사항을 설명하지만 같은 개념은 아니다. 일부 시스템 기능은 특정 사용자 시나리오에 직접 드러나지 않을 수도 있다.

개발을 진행하는 두 가지 관점

유스케이스 주도 개발

애플리케이션의 유스케이스에서 한 번에 하나의 시나리오에 집중한다. 보통 한 유스케이스의 주요 시나리오를 구현한 뒤 다음 유스케이스로 이동한다.

특징 주도 개발

하나의 특징을 완성한 뒤 다른 특징으로 이동한다. 특징의 크기와 관계없이 한 번에 하나에 집중하며, 큰 그림을 살핀 후 작은 기능 단위로 반복 개발한다.

어떤 방식을 택하더라도 개발 주기의 각 단계에서 분석과 설계를 계속 수행해야 한다.

테스트와 테스트 주도 개발

테스트는 소프트웨어가 기대한 대로 동작한다는 근거를 제공하고 회귀를 빠르게 발견하게 해 준다. 다만 테스트가 모든 버그의 부재를 증명하는 것은 아니다.

좋은 테스트는 하나의 구체적인 행동에 집중한다. 테스트 대상에 따라 한 클래스의 메서드 몇 개만 다룰 수도 있고, 여러 클래스의 협력을 함께 검증할 수도 있다.

테스트 주도 개발(Test-Driven Development, TDD)은 실패하는 테스트를 먼저 작성한 뒤, 테스트를 통과하는 최소한의 코드를 구현하고 구조를 개선하는 과정을 반복한다.

Text실패하는 테스트 작성 → 테스트 통과 → 리팩터링 → 반복

계약에 의한 설계와 방어적 프로그래밍

접근 방식전제일반적인 처리
계약에 의한 설계(Design by Contract)호출자와 메서드가 사전 조건, 사후 조건, 불변식을 지킨다.계약 위반을 명확한 오류나 예외로 드러낸다.
방어적 프로그래밍외부 입력이나 협력 객체가 잘못된 값을 전달할 수 있다.입력을 검증하고 오류를 처리하거나 안전한 대체 값을 사용한다.

두 방식은 대립 관계가 아니다. 신뢰 경계와 실패 비용에 따라 계약을 명확히 하면서도 필요한 곳에서는 방어적으로 검증할 수 있다.

다형성

다형성은 하위 타입의 객체를 상위 타입이 필요한 자리에 사용할 수 있게 하는 성질이다. 클라이언트가 구체적인 클래스가 아니라 공통 인터페이스에 의존하면, 기존 코드를 크게 바꾸지 않고도 새로운 구현을 추가할 수 있다.

핵심 정리

  • 변하는 부분을 캡슐화해 변경의 영향을 좁힌다.
  • 구현보다 인터페이스에 의존해 확장 가능성을 높인다.
  • 책임을 분명하게 나누어 응집도를 높이고 결합도를 낮춘다.
  • 요구사항과 도메인을 충분히 분석한 뒤 객체와 관계로 옮긴다.
  • 분석, 설계, 구현, 테스트를 짧은 주기로 반복한다.
  • 좋은 소프트웨어는 고객이 원하는 일을 수행하면서도 변경과 확장이 쉽다.
